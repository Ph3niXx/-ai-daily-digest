Jobs Radar : d'une routine Cowork token-vore
à une routine Claude Code sur API

On remplace la routine Cowork (Sonnet + navigateur + session LinkedIn) par une routine Claude Code planifiée qui lit une API jobs structurée en JSON et abandonne l'intel réseau warm. La token-vore venait des écrans LinkedIn rendus et du graphe social navigué — les deux disparaissent.

Réconciliation post-implémentation (28 mai 2026 · ADR-19). Le moteur a shippé tel que désigné ici — routine Claude Code distante (claude.ai, trigger trig_01JtTsMm27eTAGxR5po5KmMQ, Sonnet 4.6) qui fetch JSearch via curl et écrit jobs/job_scans via le connecteur MCP Supabase. Un plan intermédiaire (GitHub Actions + Gemini) a été écrit puis abandonné (jamais construit). Corrections de détail : la clé RapidAPI n'est pas un secret GitHub mais vit inline dans le prompt de la routine (un agent distant ne lit pas les secrets GitHub) ; coût réel couvert par le plan Max (0 €/run, pas « cents/run ») ; intel_depth toujours light ; job_scans sans signal_cv ; détection auto de clôture abandonnée → closed_at front-only.

Le problème

La routine actuelle tourne dans Cowork desktop avec Sonnet et un navigateur sur une session LinkedIn authentifiée. Elle est token-vore pour deux raisons cumulées :

  • Lecture d'écrans LinkedIn rendus — chaque page de recherche ou fiche de poste est un DOM gigantesque plein de bruit, ingéré tel quel par le modèle.
  • Navigation du graphe social — pour produire l'intel warm (lead identifié, réseau 1er/2e degré, angle d'approche), l'agent visite des pages entreprise et des profils, multipliant les écrans lourds.

S'y ajoute la dépendance opérationnelle : Cowork desktop allumé + un Chrome connecté à LinkedIn.

Architecture cible

Principe directeur : on ne change que qui remplit les tables et comment. Les tables jobs + job_scans, le front Jobs Radar et le realtime Supabase restent la cible.

Front Jobs Radar — inchangé (la carte hot dégrade proprement)

Couche source — JSearch (RapidAPI)

  • Endpoint search, country=fr, num_pages=1 (≈10 offres/requête). Une requête par rôle cible — 5 rôles : product manager, senior program manager, transformation program manager, release train engineer, chief of staff. (head of product + senior PO fintech retirés, couverts par product manager.)
  • JSON par offre : job_id, employer_name, job_title, job_description, job_apply_link, parfois le salaire.
  • Clé RapidAPI : inline dans le prompt de la routine, pas un secret GitHub (un agent distant ne les lit pas).
Quota. Free tier ≈ 100 req/mois (à confirmer — sources entre 100 et 200). Cadence retenue : 4 runs/semaine × 5 requêtes ≈ 87/mois, sous le cap même pessimiste (~13 de marge). num_pages=1 ⇒ 1 requête = 1 appel (évite la multiplication du quota par page, piège connu de JSearch). Plan B si le quota se révèle être 100 pile ou si le besoin de quotidien revient : bascule Adzuna (gratuit, quota bien plus large, couverture produit/RTE Paris moindre) — code de fetch quasi identique.

Couches scoring & écriture — quasi inchangées (+ skills)

Les Étapes 0, 3 et 4.5 du prompt v3.2 sont reprises telles quelles (calibrage, rubric 3 axes + bonus, estimation salaire). Seule différence : le modèle score sur le texte renvoyé par l'API, plus sur une page rendue. Ajout : au même passage, l'agent extrait les skills de la JD et les confronte à skill_radar + user_profile (présent / à acquérir), stockés dans intel.skills_required[]. UPSERT et garde-fous user-modifiables (status, user_notes, user_verdict*) identiques ; le trigger jobs_inherit_user_status continue de marcher.

Ce qui change concrètement

✕ Disparaît du prompt
  • Intel light + deep (signaux boîte, lead, réseau warm, angle, maturité SAFe).
  • Fenêtre LinkedIn f_TPR → remplacée par la fraîcheur native de l'API.
  • Passe de fraîcheur par re-fetch de pages (exigeait le navigateur).
✓ Conservé
  • Nouveau — skills attendus × match CV (✓ tu as / ↗ à acquérir), extraits de la JD.
  • Score + rubric par axe, salaire estimé.
  • Bouton « Marquer clôturée » manuel (ADR-18) — remplace la détection auto.
  • GUARD anti-injection sur le texte des JD (par prudence).

Impact données

  • intel jsonb = salary_estimate + skills_required[] (skills de la JD, flag on_cv par skill via skill_radar + user_profile) ; intel_depth ∈ {none, light}.
  • linkedin_job_id (UNIQUE) stocke l'ID JSearch ; url = job_apply_link.
  • Migration optionnelle : colonne source pour la provenance (les 554 lignes historiques restent). À trancher dans le plan — le front ne la lit pas.

Impact front — minimal

Le front gère déjà l'absence des champs intel (guards intel && (…)), donc la carte hot dégrade proprement vers score + rubric + salaire + boutons. Nettoyage du code mort : retirer le rendu intel warm de HotLeadCard, la normalisation correspondante dans transformJobIntel, et les règles CSS jr-intel-*/jr-lead-*/jr-warm-* orphelines. On conserve ScoreChip, RubricBlock, SalaryEstimate, JrVote, le scan banner et les filtres.

Impact doc / archi (règles cardinales)

  • Spec : MAJ docs/specs/tab-jobs.md + bump index.json.
  • Routine : réécrire docs/cowork-routines/jobs-radar.md en prompt Claude Code (renommage cowork-routines/ → agent-routines/ à trancher).
  • Archi : pipelines.yaml + dependencies.yaml + ADR-19 dans decisions.md.
  • Secrets : aucun secret RAPIDAPI_KEY (clé inline dans le prompt) — note dédiée dans docs/secrets.md.

Hors scope & risques

Hors scope (volontaire)

  • Enrichissement à la demande via Jarvis local — abandonné, pas remis en TODO.
  • Refonte du scan banner / filtres / vote.
  • Migration des 554 lignes historiques.

Risques assumés

  • Couverture ≠ LinkedIn : offres non 100 % LinkedIn, liens « Postuler » variés.
  • Quota free tier → fallback Adzuna.
  • Perte de la clôture auto → compensée par le bouton manuel.
  • JD tronquées → fetch d'appoint de l'URL en dernier recours.
