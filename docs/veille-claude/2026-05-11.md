### [HIGH · M] Dreaming pour Claude Managed Agents : self-improvement par revue nocturne des sessions

**Source** — [Blog Claude](https://claude.com/blog/new-in-claude-managed-agents) · [Doc Dreams](https://platform.claude.com/docs/en/managed-agents/dreams) · [Live blog Simon Willison](https://simonwillison.net/2026/May/6/code-w-claude-2026/) · [Anthropic dreaming feature - VentureBeat](https://venturebeat.com/technology/anthropic-introduces-dreaming-a-system-that-lets-ai-agents-learn-from-their-own-mistakes)

Annoncé en research preview au Code w/ Claude SF le 6 mai. Dreaming est un processus planifié (typiquement nocturne) qui relit les sessions précédentes d'un agent + ses memory stores, extrait des patterns récurrents (erreurs répétées, workflows convergents, préférences partagées entre agents) et restructure la mémoire pour qu'elle reste high-signal au fur et à mesure de la croissance. Mode automatique ou avec review manuelle des changements avant write. Memory (sept 2025) capture ce que l'agent apprend en cours de session ; Dreaming refine cette mémoire entre sessions. Étude de cas Harvey (cabinet juridique) : completion rate ×6 avec Dreaming activé, l'agent retient des workarounds spécifiques au type de fichier et des patterns tool-specific. Accès sur demande via formulaire.

> **How to apply** : c'est exactement le pattern que `nightly_learner.py` implémente côté Jarvis (extraction faits + entités depuis conversations / fenêtre / Outlook, scheduler asyncio à minuit). 3 leçons à intégrer dans la couche Jarvis sans attendre l'accès Dreaming : (1) ajouter une notion de **review-before-commit** — actuellement le nightly_learner upsert direct dans `profile_facts` / `entities`, alors qu'un mode "queue + validation manuelle dans le panel Profil" éviterait les hallucinations de faits persistées en silence ; (2) ajouter une passe de **détection de patterns récurrents** — pour l'instant on extrait des faits atomiques, pas des workflows convergents ("Jean ouvre toujours le panel Stacks après la Veille IA" serait un pattern Dreaming-style à mettre dans `profile_facts` comme méta-fait) ; (3) mettre **shared memory** entre observers — actuellement window / Outlook / conversations alimentent silos séparés, alors qu'un pattern type "réunion Slack → Outlook follow-up → conversation Jarvis avec questions précises sur le sujet" est invisible à chaque observer isolé.

> **Trend** : 6ᵉ produit Anthropic en 8 mois qui internalise une couche infra agent (Routines avril, Scheduled Tasks mars, Managed Agents avril, Memory sept, persistent thread Cowork avril, désormais Dreaming). Le verrou progressif sur la stack agent est explicite — décision stratégique à arbitrer dans 3-6 mois pour le cockpit.

### [HIGH · XS] Thariq Shihipar (Anthropic) : "L'efficacité déraisonnable de HTML" — défaut à HTML, plus Markdown, pour les sorties Claude

**Source** — [Simon Willison link post](https://simonwillison.net/2026/May/8/unreasonable-effectiveness-of-html/) · [Thread Thariq Shihipar](https://twitter.com/trq212/status/2052809885763747935) · [Galerie d'exemples](https://thariqs.github.io/html-effectiveness/)

Article (8 mai) d'un ingénieur de l'équipe Claude Code à Anthropic défendant HTML comme format de sortie par défaut, plutôt que Markdown — un renversement de pratique vis-à-vis de l'ère GPT-4 où la token-efficiency de Markdown justifiait le compromis. Argument : Claude peut désormais drop des diagrammes SVG inline, des widgets interactifs, de la navigation in-page, du color-coding par sévérité. Prompt exemple proposé : `Help me review this PR by creating an HTML artifact that describes it. I'm not very familiar with the streaming/backpressure logic so focus on that. Render the actual diff with inline margin annotations, color-code findings by severity and whatever else might be needed to convey the concept well.` Simon Willison renforce : pour les questions ad hoc à Claude, demander HTML plutôt que Markdown ouvre la porte à des explications interactives qu'on jetait jusque-là dans des artifacts séparés.

> **How to apply** : 3 endroits concrets dans le projet où je dois switcher mes prompts de "Markdown" à "HTML stylé" : (1) **panel Brief du jour** — les sections générées par Gemini Flash-Lite sont actuellement du HTML, mais quand je demande à Claude (Cowork) d'enrichir un brief ad hoc, je formule en Markdown — switcher vers HTML pour bénéficier de mini-diagrammes inline (timeline visuelle des articles, gauge de progression du radar) ; (2) **revue de PR personnelles** — le prompt template que j'utilise dans Claude Code pour `/review` ou pour audit avant merge demande un résumé Markdown — switcher vers une demande explicite "HTML artifact avec annotations inline" pour les PRs touchant `cockpit/lib/` ou `sql/*` (paths sensibles) ; (3) **briefs Jarvis (`activity_briefs`)** — le `daily_brief_generator.py` génère déjà du HTML, c'est OK, mais on pourrait y ajouter une instruction explicite "include SVG inline pour la timeline" plutôt que la liste à puces actuelle.

> **Trend** : convergence du "vibe coding" et de l'"agentic engineering" pointée par Simon Willison la veille (6 mai, item dédié dans claude_general ci-dessous) — les outils Claude deviennent assez fiables pour qu'on cesse de relire chaque ligne, donc autant maximiser la densité d'info dans les sorties.

### [HIGH · M] Multi-agent orchestration en public beta : lead agent + specialists en parallèle sur filesystem partagé

**Source** — [Blog Claude](https://claude.com/blog/new-in-claude-managed-agents) · [Doc multi-agent](https://platform.claude.com/docs/en/managed-agents/multi-agent) · [Live blog Simon Willison](https://simonwillison.net/2026/May/6/code-w-claude-2026/)

Annoncé public beta au Code w/ Claude SF le 6 mai (après research preview en avril). Un lead agent décompose une tâche, délègue chaque morceau à un specialist (modèle + prompt + tools dédiés). Les specialists travaillent en parallèle sur un filesystem partagé et contribuent au contexte du lead. Persistence : événements stockés, chaque agent garde sa mémoire — le lead peut re-checker un specialist mid-workflow. Traçage complet dans le Claude Console (qui a fait quoi, dans quel ordre, pourquoi). Démo keynote : Commander / Detector / Navigator pour landing de drones lunaires. Cas Netflix : analyse de logs de centaines de builds en parallèle, surface uniquement les patterns récurrents qui touchent >N applications.

> **How to apply** : applicable à `weekly_analysis.py` qui fait actuellement 6 passes séquentielles (wiki, signals, recommendations, challenges, opportunities, RTE) sur Claude Haiku 4.5 avec budget $1/run. Réécrire en pattern multi-agent : 1 lead = arbitre du budget + assembleur de l'output Markdown, 6 specialists parallèles = un par section, chacun avec son system prompt focalisé. Gains attendus : (a) réduction latence (parallèle au lieu de séquentiel — typique 8min → 2min), (b) prompts plus courts par specialist donc moins de token burn, (c) en cas d'échec d'un specialist, le lead peut relancer juste celui-là plutôt que repartir de zéro. Calibre du POC : implémenter sur une branche `feat/multi-agent-weekly`, comparer 4 runs côte-à-côte (séquentiel actuel vs multi-agent) sur tokens, durée, et qualité humaine notée 1-5 par section. Si gain >30% sur durée ET qualité ≥ baseline, merger.

> **Trend** : pattern "thin client local + heavy parallel cloud" continue de se cristalliser (ultrareview en mai 4, ultraplan en avril, désormais multi-agent en beta). 3ᵉ commande/pattern Anthropic en 5 semaines qui externalise du travail vers agents cloud parallélisés.

Header `anthropic-beta: advisor-tool-2026-03-01`, déclaration `advisor_20260301` dans le tools array du Messages API, paramètre `max_uses` pour cap dur.

> **How to apply** : utilisable directement sur `weekly_analysis.py` qui tourne sur Claude Haiku 4.5 avec un `CostTracker` qui arrête le pipeline si on dépasse 1$. Ajouter un advisor Opus 4.6 avec `max_uses=3` : Haiku exécute les 6 passes, escalade à Opus pour les décisions stratégiques (par exemple "quel use case RTE retenir parmi ces 5 candidats", "quel challenge calibrer pour cette semaine vs le profil"). Coût attendu : +0.05-0.10$/run (3 advisor calls × ~500 tokens × tarif Opus), donc nouveau budget cible 1.10$/run, à confirmer après le 1ᵉʳ run. Suivi tokens via le bloc `usage.advisor_tokens` séparé. Si la qualité subjective des recommendations/challenges progresse (à apprécier sur 2-3 runs), garder. Sinon revenir à Haiku seul.

> **Trend** : Anthropic transforme la composition de modèles en primitive API (advisor tool 1-line) plutôt qu'en pattern à implémenter en code. 2ᵉ primitive de ce type en 2 mois après les sub-agents formels en mars. Réduit la barrière à l'expérimentation cost/quality.

### [MEDIUM · XS] Claude Code : `ENABLE_PROMPT_CACHING_1H` + `FORCE_PROMPT_CACHING_5M` pour reprendre le contrôle du cache TTL

**Source** — [Doc Claude Code model-config](https://code.claude.com/docs/en/model-config) · [Issue 48082 GitHub](https://github.com/anthropics/claude-code/issues/48082) · [Theermite analyse](https://theermite.com/en/blog/claude-code-prompt-caching-explained-why-enable-prompt-caching-1h-matters-moa1xw0m)

Documentation enrichie en mai 2026 (issue #48082 ouverte le 1er mai, fix doc livré v2.1.130 le 5 mai). Deux env vars complémentaires sortent enfin de l'ombre — la régression cache TTL 1h→5min de fin mars (couvert dans la veille du 25 avril) avait laissé un trou de configuration. `ENABLE_PROMPT_CACHING_1H=1` réactive le cache 1h sur API key, Bedrock, Vertex et Foundry — cible les sessions intermittentes (>5min mais <1h entre deux appels). `FORCE_PROMPT_CACHING_5M=1` force le cache court même quand le modèle aurait choisi long — cible les sessions intensives bursty où on rotate beaucoup de contextes différents et où le cache long pollue.

> **How to apply** : pour MA stack cockpit où je relis CLAUDE.md (~700 lignes) + un sous-ensemble de `docs/architecture/` + 2-3 specs `docs/specs/` à chaque session, le cache 5min par défaut expire pendant que je lis l'output, donc je re-paie le system prompt à la relance — typiquement 30-50% du coût session sur les petites itérations. Action concrète : ajouter `export ENABLE_PROMPT_CACHING_1H=1` dans mon `.zshrc` (ou `setx ENABLE_PROMPT_CACHING_1H 1` côté PowerShell Windows si Jarvis tourne sur Windows). Mesurer après 1 semaine : grep les logs Claude Code (`~/.claude/logs/`) pour comparer le `cache_creation_input_tokens` vs `cache_read_input_tokens`. Si ratio cache_read passe de ~40% à ~70%, garder.

> **Trend** : 4ᵉ ajustement pricing/perf Claude Code en 2 mois (cache TTL nerf en mars, pricing flip Pro→Max en avril, MCP auto-retry x3 en mai, cache 1h documenté en mai). Le contrôle des coûts via env vars devient une compétence opératoire à part entière.
