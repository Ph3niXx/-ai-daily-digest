# Architecture Decision Records (léger)

Format court : **Contexte** (pourquoi se pose la question) → **Décision** (ce qu'on fait) → **Conséquences** (coûts / contraintes / choix que ça ferme). Datées, pas numérotées — l'ordre chronologique suffit.

## ADR-01 · 2025-Q4 · Hébergement front sur GitHub Pages

- **Contexte** : besoin d'un cockpit perso déployable sans infra, pas de build CI lourd, accessible depuis mobile.
- **Décision** : GitHub Pages servit en statique, coquille `index.html` + React 18 via `@babel/standalone` sur unpkg. No-build-step.
- **Conséquences** : CSP doit autoriser `unsafe-eval` (Babel standalone) ; pas de tree-shaking ; chaque `.jsx` expose son composant sur `window.X` pour être visible par les autres scripts ; itération possible en `file://` local sans serveur.

## ADR-02 · 2025-Q4 · Supabase comme backend unique

- **Contexte** : stockage structuré des articles, métriques et conversations + auth Google + RLS granulaire, sans ouvrir un serveur perso.
- **Décision** : Supabase free tier, Postgres + pgvector + Auth Google + Realtime. Toute la donnée structurée y vit.
- **Conséquences** : une seule cible de RLS à auditer ; quotas 500 MB / 50k MAU à surveiller (panel Stacks) ; dépendance cloud unique — si Supabase tombe, Jarvis local reste dispo mais le cockpit lit vide.

## ADR-03 · 2026-Q1 · Split Gemini (daily) / Claude (weekly)

- **Contexte** : la veille quotidienne traite ~150 articles / jour (enrichissement, classification, brief) — incompatible avec le budget Claude. Mais les analyses hebdo (signaux, opportunités, challenges, recos) demandent un modèle de bien meilleure qualité.
- **Décision** : Gemini 2.5 Flash-Lite (free tier 1000 req/jour) pour tout le volume daily. Claude Haiku 4.5 (budget ~0,03 $/run, cap 1 $) pour la cognition hebdo.
- **Conséquences** : deux clients, deux clés, deux pipelines à logger distinctement (tables `gemini_api_calls` + `weekly_analysis.tokens_used`). Panel Stacks agrège les deux. Si Gemini tombe, le daily a un fallback `_fallback_brief_html` qui construit un brief minimal depuis les articles RSS.

## ADR-04 · 2026-Q1 · Pipelines backend en `service_role`, front en `authenticated`

- **Contexte** : les pipelines GitHub Actions tournent sans session `auth.uid()` — ils ne peuvent pas être des utilisateurs `authenticated`. Le front lui a une session Google OAuth.
- **Décision** : migration `sql/006_rls_authenticated.sql` — toutes les tables exigent `authenticated` pour SELECT. Les tables éditées par le front (~16 aujourd'hui : `business_ideas`, `user_profile`, `skill_radar`, `weekly_opportunities`, `learning_recommendations`, `challenge_attempts`, `wiki_concepts`, `commitments`, `uncomfortable_questions`, `gaming_wishlist`, `history_notes`, `claude_veille`, `claude_ecosystem`, `profile_facts`, `usage_events`, `jobs`) ont aussi INSERT/UPDATE `authenticated` — voir `dependencies.yaml::panels[].writes` pour la liste vivante. Les pipelines utilisent `SUPABASE_SERVICE_KEY` qui bypass RLS.
- **Conséquences** : anon ne peut plus rien lire (fini le partage public du cockpit sans login) ; `start_jarvis.bat` refuse de démarrer sans `SUPABASE_SERVICE_KEY` en env ; chaque nouvelle table ajoutée doit explicitement configurer ses policies (cf. migrations récentes). Exception : `jobs` et `job_scans` sont en `using(true)` (pas restreints `authenticated`) — divergence assumée pour la routine Cowork qui pousse en service_role mais pour laquelle l'écriture reste whitelistée côté front sur `status` + `user_notes`.

## ADR-05 · 2026-Q1 · Data layer front à deux tiers

- **Contexte** : certains panels (Brief, Ma semaine, Radar) doivent s'afficher instantanément au premier écran. Les autres peuvent charger à la demande. Charger 40 tables au boot = latence inacceptable.
- **Décision** : **Tier 1** (bootstrap.js → bootTier1) charge 7 tables en parallèle AVANT le mount React ; **Tier 2** (loadPanel) charge le corpus d'un panel à son premier clic sidebar, mémoïsé via `once()` le reste de la session.
- **Conséquences** : chaque panel déclare explicitement s'il est Tier 1 ou Tier 2 ; cache Tier 2 est invalidé seulement au reload (pas de cache busting sélectif) ; un nouveau panel par défaut est Tier 2 sauf décision contraire.

## ADR-06 · 2026-Q1 · Jarvis local FastAPI + tunnel Cloudflare optionnel

- **Contexte** : on veut un assistant IA perso qui connaît nos faits, avec RAG sur notre corpus Supabase. Un SaaS type ChatGPT ne peut pas (privacy + coût).
- **Décision** : `jarvis/server.py` (FastAPI uvicorn port 8765) appelle LM Studio local (Qwen3.5 9B) ou Claude Haiku selon le mode. Le cockpit appelle `POST /chat` — localhost d'abord, puis tunnel Cloudflare en fallback quand le cockpit tourne sur GitHub Pages (HTTPS interdit le mixed-content vers `http://localhost`).
- **Conséquences** : l'utilisateur doit lancer `start_jarvis.bat` pour que Jarvis réponde ; URL du tunnel est publiée dans `user_profile.jarvis_tunnel_url` ; si tunnel down, fallback heuristique local dégradé (mode Pratique des challenges surtout).

## ADR-07 · 2026-Q2 · Observers privacy-first (données locales uniquement)

- **Contexte** : Jarvis a besoin de comprendre ce que l'utilisateur fait en ce moment (fenêtre active, calendrier, mails) pour répondre pertinemment. Mais on ne veut PAS que ces données partent sur un serveur tiers.
- **Décision** : observers (`window_observer.py`, `outlook_observer.py`) stockent les données brutes dans `jarvis_data/*.jsonl` / `.json` locaux, jamais versionnés. Seul un résumé quotidien agrégé (`activity_briefs`) monte dans Supabase, via `daily_brief_generator.py` à 18h.
- **Conséquences** : les titres de réunions et apps actives restent sur la machine locale ; si on change de machine, tout l'historique d'activité brute est perdu (résumés conservés) ; le `nightly_learner.py` qui extrait les faits depuis ces JSONL doit tourner sur la machine qui les produit.

## ADR-08 · 2026-Q2 · Pipelines perso séparés, pas de monolithe sync.py

- **Contexte** : au début on avait `main.py` qui faisait tout (RSS + stats perso). Devenu ingérable, différents rythmes, différentes APIs, différents formats.
- **Décision** : un `pipelines/<source>_sync.py` par source externe (Strava, Withings, Last.fm, Steam, Sport RSS, Gaming RSS, Anime RSS, News RSS), chacun avec son workflow YAML dédié et son cron propre. `requirements-<source>.txt` isolé pour éviter les conflits de deps.
- **Conséquences** : 10 pipelines au lieu d'un, mais chacun petit et testable indépendamment ; coût : 10 workflows à maintenir ; un bug sur Strava ne casse pas Last.fm.

## ADR-09 · 2026-Q2 · Stockage brut + mappé pour chaque source externe

- **Contexte** : les APIs externes évoluent (Strava change ses schémas, Withings ajoute des champs). Si on ne stocke que la forme mappée, on perd l'info.
- **Décision** : chaque source a DEUX tables — `<source>_raw` (payload JSONB complet, service_role only) et `<source>_<entity>` (colonnes typées lues par le front). Le pipeline upsert les deux.
- **Conséquences** : double stockage donc coût disque + ; mais on peut toujours re-mapper sans refetch depuis l'API (précieux sur les APIs à rate-limit sévère type Strava).

## ADR-10 · 2026-Q2 · pgvector + indexer Jarvis unifié

- **Contexte** : Jarvis a besoin de RAG sur articles + wiki + opportunités + idées + RTE + profil. Utiliser 6 tables distinctes pour l'embedding serait ingérable.
- **Décision** : une table `memories_vectors` unique (source_table + source_id + chunk_text + embedding vector(1024) + metadata JSONB). `jarvis/indexer.py` indexe périodiquement chaque table source. Fonction RPC `match_memories()` pour la recherche sémantique.
- **Conséquences** : un seul index à gérer ; dimension 1024 figée (modèle Qwen3-Embedding-0.6B) — changer de modèle = réindexer tout ; `check_index_freshness.py` compare les COUNTs source vs `memories_vectors` au boot de Jarvis.

## ADR-11 · 2026-Q2 · Télémétrie append-only dans `usage_events`

- **Contexte** : on veut savoir ce que l'utilisateur fait dans le cockpit (sections visitées, actions, erreurs) sans maintenir un SaaS analytics.
- **Décision** : table `usage_events` append-only (INSERT authenticated, pas de UPDATE/DELETE enforcé par RLS). Le front envoie via `track(event_type, payload)` best-effort. Un échec de télémétrie ne casse jamais le cockpit.
- **Conséquences** : données rétrocompatibles par construction (JSONB `payload` extensible) ; panel Historique consomme directement `usage_events` pour les "actions du jour" ; ajouter un nouvel `event_type` demande de mettre à jour le tableau dans CLAUDE.md.

## ADR-12 · 2026-Q2 · Specs produit par onglet + lint bloquant

- **Contexte** : les 29 onglets du cockpit dérivaient vite du code — personne ne savait ce qu'ils étaient censés faire.
- **Décision** : un `docs/specs/tab-<slug>.md` par onglet, source de vérité consommée en direct par Jarvis Lab. Sections `Fonctionnalités` et `Parcours utilisateur` écrites en vocabulaire produit (pas de chemins `.jsx`, pas de `Tier 1`, pas de colonnes DB). Lint bloquant CI (`lint_specs_produit.py`).
- **Conséquences** : toute PR de code à impact sur un onglet doit updater son spec dans le même commit ; drift automatiquement détecté par `spec-drift-check.yml` ; lint CI bloque les régressions de vocabulaire.

## ADR-13 · 2026-Q2 · Architecture en YAML, rendu SVG maison (pas Mermaid)

- **Contexte** : on veut une vue archi dans Jarvis Lab, versionnée, avec des règles de routage strictes (pas de diagonales, trois types d'arêtes dans trois couloirs, labels verticaux à gauche). Mermaid ne sait pas faire proprement, et son thème ignore nos CSS variables Dawn/Obsidian/Atlas.
- **Décision** : `docs/architecture/*.yaml` déclaratif, rendu par un composant React custom qui calcule les positions et les rails de routage. js-yaml côté client pour parser. Lint `validate_architecture.py` + arch-drift-check côté CI.
- **Conséquences** : écrire le renderer maison = 500+ lignes de SVG layout ; mais on contrôle le routage à 100 % et on hérite des 3 thèmes gratos via `var(--acc)` ; ajouter une 5e boîte à une couche redistribue automatiquement les colonnes.

## ADR-14 · 2026-Q2 · Budget dur 3 €/mois, tracking Stacks

- **Contexte** : projet perso, pas question de se retrouver avec une facture 30 € pour avoir oublié de capper un quota.
- **Décision** : budget mensuel hard à 3 € (Claude Haiku weekly + Jarvis cloud occasionnel). `CostTracker` dans `weekly_analysis.py` arrête le pipeline si le budget hebdo dépasse 1 $. Panel Stacks agrège les coûts réels + projection 7j.
- **Conséquences** : les analyses hebdo peuvent s'arrêter avant d'être complètes certains runs ; on est forcé à écrire des prompts compacts ; Gemini free tier reste la cheville ouvrière.

## ADR-16 · 2026-05-21 · Calibrage Jobs Radar par feedback utilisateur

- **Contexte** : le scoring Cowork (0-10) est calculé sans retour utilisateur — après 2 mois d'usage, le radar remonte des offres systématiquement mal scorées (trop junior, mauvais secteur). On veut un signal de calibrage sans créer un nouveau pipeline.
- **Décision** : signal 👍/👎 + raison persisté sur 3 nouvelles colonnes de la table `jobs` (`user_verdict` text, `user_verdict_reason` text, `user_verdict_at` timestamptz — migration 014, `sql/014_jobs_feedback.sql`). Héritage du verdict sur republication LinkedIn dans la même fenêtre 180j (extension du trigger `jobs_inherit_user_status`). Préférences utilisateur découpées en deux clés `user_profile` : `job_pref_rules` (règles verouillées par l'utilisateur, non écrasables) et `job_pref_observed` (profil inféré et maintenu par la routine Cowork à chaque run). La synthèse feedback → ajustement score s'exécute à l'intérieur du run Cowork quotidien existant, sans nouveau pipeline. Pas de second score : le verdict ajuste directement `score_total` au prochain scan. Effet asynchrone : un vote aujourd'hui influe sur le scan du lendemain.
- **Conséquences** : trois colonnes nullable sur `jobs` (whitelist front élargie) ; routine Cowork versionnée à mettre à jour (`docs/cowork-routines/jobs-radar.md`) pour lire `job_pref_rules` + `job_pref_observed` + les verdicts récents avant scoring ; `user_profile` gagne deux clés JSONB structurées à documenter dans la spec profil ; fenêtre d'héritage passée de 30j (archived) à 180j pour couvrir les verdicts.

## ADR-18 · 2026-05-27 · Clôture manuelle — le front écrit `closed_at`

- **Contexte** : ADR-17 a posé `closed_at` en écriture Cowork seule (lecture seule côté front). La détection reste asynchrone — une offre clôturée peut traîner dans le feed plusieurs jours avant la passe de fraîcheur, et l'utilisateur n'a aucun moyen de la masquer immédiatement quand il tombe sur le mur LinkedIn.
- **Décision** : le cockpit peut désormais écrire `closed_at` via un bouton « Marquer clôturée » (et « Rouvrir » qui le remet à NULL). `closed_at` rejoint la whitelist `patchJobSupabase` (comme `user_verdict*` avant lui). **Renverse** la conséquence d'ADR-17 « jamais écrit par le cockpit ». La détection Cowork (opportuniste + passe de fraîcheur re-priorisée, cf. routine v3.2) reste en place — les deux chemins coexistent, `isDead(o)` les unifie.
- **Conséquences** : `closed_at` écrit par deux sources (Cowork auto + front manuel) ; réversibilité front (Rouvrir) ; télémétrie `jobs_action {action:"close"|"reopen"}` ; RLS `jobs` déjà permissive (`using(true)`) → pas de changement de policy ; `dependencies.yaml` whitelist à jour.

## ADR-17 · 2026-05-21 · Offres clôturées — détection Cowork + masquage front

- **Contexte** : certaines offres LinkedIn restent actives en base longtemps après que LinkedIn les ait marquées "Les candidatures ne sont plus acceptées". Le cockpit continue d'afficher ces offres mortes, polluant le feed. On ne peut pas vérifier LinkedIn en direct côté cockpit (pas d'accès authentifié, pas de scraping front possible).
- **Décision** : colonne `closed_at timestamptz` ajoutée à la table `jobs` (migration 015, `sql/015_jobs_closed_at.sql`). La routine Cowork la pose à `now()` quand elle lit "ne sont plus acceptées" / "No longer accepting applications" lors d'une visite de page d'offre (opportuniste à l'Étape 5 sur les nouvelles offres, ou lors d'une passe de fraîcheur Étape 8 sur les 25 offres actives les plus anciennes). Le front masque toute offre avec `closed_at non-null && status !== "applied"` dans le feed actif et les hot leads. Filtre "Clôturées" dédié pour les revoir. Compteur header ("N clôturées masquées") si N > 0. Une offre déjà postulée (status="applied") reste visible dans le pipeline malgré `closed_at`.
- **Conséquences** : masquage précis — jamais sur la seule ancienneté `last_seen_date` (risque de cacher des offres valides) ; effet asynchrone (délai entre la clôture LinkedIn et la détection Cowork) ; `closed_at` n'est pas dans la whitelist PATCH front (jamais écrit par le cockpit) ; la passe de fraîcheur est bornée à 25 offres/run pour tenir le budget 15 min.

## ADR-15 · 2026-Q2 · Maintenance archi versionnée avec CI arch-drift

- **Contexte** : la doc archi dérive toujours plus vite que le code. On ne veut pas reproduire l'erreur des specs onglets.
- **Décision** : workflow `arch-drift-check.yml` qui liste les chemins à impact archi (pipelines/, main.py, panel-*.jsx, migrations, workflows sync) et warn quand une PR touche l'un sans toucher `docs/architecture/`. Workflow `validate-arch.yml` bloquant sur structure des YAML. CLAUDE.md § Maintenance architecture aligné sur la section specs.
- **Conséquences** : non-bloquant au départ (`continue-on-error: true`) — on durcira après deux semaines de bruit ; la checklist par type de modif (nouveau pipeline / nouveau panel / nouvelle table) est explicite dans le README archi et dans CLAUDE.md.

## ADR-19 · 2026-05-28 · Jobs Radar — routine Claude Code distante (JSearch) remplace la routine Cowork LinkedIn

- **Contexte** : la routine Cowork (Sonnet + navigateur sur session LinkedIn, cf. [docs/cowork-routines/jobs-radar.md](../cowork-routines/jobs-radar.md)) était token-vore (~0,20-0,40 €/run) — ingestion de DOM LinkedIn rendus + navigation du graphe social pour l'intel warm — et dépendait d'un Chrome authentifié + Cowork desktop allumé. Le design du 2026-05-27 ([specs/2026-05-27-jobs-radar-api-migration-design](../superpowers/specs/2026-05-27-jobs-radar-api-migration-design.md)) proposait une routine Claude Code distante sur API jobs structurée. Un plan intermédiaire (2026-05-28) a tenté un pivot vers un cron GitHub Actions + Gemini gratuit, sur la crainte qu'un agent distant ne puisse pas s'authentifier — **plan abandonné** (cf. son bandeau SUPERSEDED).
- **Décision** : **routine Claude Code distante planifiée** (claude.ai, trigger `trig_01JtTsMm27eTAGxR5po5KmMQ`), cron `0 6 * * 1,3,5,0` (lun/mer/ven/dim 08:00 Paris), modèle **claude-sonnet-4-6**. Elle tourne dans un sandbox cloud Anthropic avec son propre checkout du repo (allowed_tools Bash/Read/Grep/Glob), **fetch JSearch (RapidAPI) via `curl`** (5 requêtes-rôles, `num_pages=1`, `country=fr`, ~87 req/mois sous le tier gratuit), score la rubric /10 + extrait 5-9 skills (flag `on_cv` vs `skill_radar`/`user_profile`) + estime le salaire, puis **lit/écrit `jobs` + `job_scans` via le connecteur MCP Supabase** (`execute_sql`). Réalise le design 2026-05-27.
- **Résolution des deux contraintes** (qui avaient motivé le faux pivot GH Actions) : (1) **pas de secret GitHub lisible par un agent distant** → la clé RapidAPI est portée **en clair dans le prompt de la routine** (config claude.ai privée) et Supabase est joint via le **connecteur MCP** (auth propre, pas de `SUPABASE_SERVICE_KEY` en env) ; (2) **pas de coût LLM récurrent** → la routine est **couverte par le plan Max** (pas de facturation par run comme l'API). Le pivot Gemini devient donc inutile — on garde Sonnet (qualité de scoring) à coût marginal nul.
- **Conséquences** : 0 €/run effectif (plan Max ; à partir du 2026-06-15, pool de crédits Agent SDK séparé mais empreinte faible). Abandon de l'**intel warm** (signaux boîte / lead / réseau / angle / maturité SAFe) et de la **reco CV** (`cv_recommended`/`cv_reason` plus écrits, cf. refonte front). `intel` jsonb = `{ salary_estimate, skills_required:[{name,on_cv}] }`, `intel_depth = 'light'`. **Détection auto de clôture supprimée** (plus de navigateur) → `closed_at` devient front-only via le bouton manuel (**renverse** la part « Cowork auto » d'ADR-17/ADR-18). Couverture élargie hors LinkedIn (liens « Postuler » parfois Indeed/WTTJ). `linkedin_job_id` stocke l'id JSearch. Match `on_cv` sans CV dans le cloud (basé sur `skill_radar`/`user_profile`). Clé RapidAPI à régénérer si elle a fuité (elle vit dans le prompt + transcripts). `pipelines.yaml` la liste sous `external_routines:` (hors timeline GHA) ; `dependencies.yaml` owner `jobs_radar_routine`.

## ADR-20 · 2026-05-28 · Jobs Radar v2.1 — exploitation des champs JSearch (remote, skills depuis l'annonce, filtre fulltime)

- **Contexte** : la routine (ADR-19) n'exploitait qu'une fraction du JSON JSearch (titre, boîte, description, ville, date, lien, salaire). Champs inutilisés à valeur : `job_is_remote` (préférence géo de Jean), `job_highlights` (`{Qualifications, Responsibilities, Benefits}` — source **structurée** des compétences, plus propre que la description brute), `job_employment_types` (filtrer le non-permanent), `employer_logo` (UX). Quota réel mesuré : **200 req/mois** (pas ~100), large marge.
- **Décision** : (1) **Filtre dur FULLTIME** avant scoring/insertion — les offres dont `job_employment_types` est renseigné et exclut FULLTIME (INTERN/PARTTIME/CONTRACTOR) sont écartées (gardées si le champ est absent). Conséquence : `employment_type` n'a **pas** de colonne (toutes les lignes sont FULLTIME). (2) **Skills depuis `job_highlights.Qualifications`/`Responsibilities` en priorité**, fallback `job_description` ; provenance tracée dans `intel.skills_source`. (3) **`job_is_remote` → colonne `jobs.is_remote boolean`** (migration `sql/016_jobs_is_remote.sql`) — badge « Remote » + filtre front ; **n'influe pas sur le score** (la géo reste gérée par le calibrage `job_pref_rules`). (4) **`employer_logo` → `intel.employer_logo`** (affichage seul, jsonb, pas de colonne).
- **Conséquences** : data contract `intel` étendu = `{ salary_estimate, skills_required:[{name,on_cv}], skills_source, employer_logo }`. Nouvelle colonne `is_remote` (lecture seule front, hors whitelist PATCH). Filtre fulltime = moins de bruit mais dépend d'un champ JSearch parfois absent (garde-fou : on garde si inconnu). Skills plus fiables quand `job_highlights` est rempli (variable selon les offres). Prompt de la routine (Étapes 1 / 1.5 / 3 / 4) mis à jour ; front (carte + filtre Remote + logo + label « d'après l'annonce ») ; `tab-jobs.md` + `dependencies.yaml` + `external_routines` à jour. `closed_at` reste front-only (inchangé vs ADR-19).

## ADR-21 · 2026-05-29 · Jobs Radar — réorientation du matching vers l'IA (requêtes + règles utilisateur)

- **Contexte** : audit du 2026-05-29 — le radar optimisait la trajectoire actuelle de Jean (RTE/PM senior → postes prestige PM/Chief of Staff) et était aveugle à son ambition déclarée (devenir expert IA, en CDI senior, potentiellement créer sa boîte). Preuves : 5 requêtes-rôles 100 % management produit/programme, **aucune requête IA** ; `ambitions`/`interests`/`what_excites_me` jamais lus par la routine ; `job_pref_rules` (clé « autorité absolue » lue à l'Étape 0) **inexistante en base** — toute la personnalisation reposait sur `job_pref_observed` (poids moindre) ; score **anti-corrélé** aux verdicts (👎 moy 8,72 > 👍 9,00 sur n=2 ; Joko CoS noté 10/10 downvoté).
- **Décision** : (1) **`user_profile.job_pref_rules` créée** — règles explicites de Jean : cap pivot IA en CDI senior ; fort bonus IA-core / apprentissage IA / scope large + exposition C-suite ; **éliminatoire** = package < 80k€ fixe **ou** < 10k€ variable, expertise verticale absente (ML eng, infra/IAM, compta, crypto/web3 pur), conseil/ESN ; secteur neutre ; remote indifférent ; **grand groupe non éliminatoire**. (2) **ÉTAPE 1 : 5 → 8 requêtes-rôles** — ajout de `AI product manager`, `AI program manager`, `head of AI product`, `generative AI product manager` ; `transformation program manager` fusionnée dans `senior program manager`. (3) **ÉTAPE 3 réorientée** : « Roles cibles » IA-first, « Secteurs chauds » IA/AI tooling/GenAI en tête, crypto/web3 déplacé en froid. Appliqué au prompt **live** via `RemoteTrigger update` (miroir [docs/cowork-routines/jobs-radar.md](../cowork-routines/jobs-radar.md)).
- **Conséquences** : quota JSearch ≈ **138 req/mois** (sous le plafond 200, ADR-20). Le scoring ne **re-score pas** le stock existant (les ~315 offres `new` gardent leur ancien score — re-boucle de calibrage = chantier futur) ; `job_pref_rules` prime sur la rubric mais n'agit qu'aux scans suivants. Remote sorti des priorités (Jean = indifférent) → **backfill `is_remote` abandonné**. `pipelines.yaml` (`external_routines`) + `tab-jobs.md` + `index.json` mis à jour. Pistes non faites : refonte **rubric FIT** (axe alignement IA + faisabilité, pénalité expertise manquante, réconcilie le score avec les verdicts), **re-scoring hebdo** du stock actif, **filtres front** (stage/lieu/verdict, « masquer mes 👎 »).
- **Addendum 2026-05-29 (exécution)** : (a) **3 des requêtes IA initiales (`AI … in France`) renvoyaient 0** sur JSearch — formulations validées et corrigées : `… Paris` et le français (`product manager intelligence artificielle`) fonctionnent ; ÉTAPE 1 utilise désormais des **requêtes complètes** (plus de suffixe `in France`), 9 requêtes, ~156 req/mois. (b) **JSearch renvoie `403 Host not in allowlist` depuis le sandbox cloud** (IP datacenter rejetée par RapidAPI) → les runs cloud (cron + manuels) échouent ; le fetch ne marche que depuis une IP autorisée. Voie durable retenue : **réactiver le cloud** via l'allowlist RapidAPI (à défaut, fetch local). Un **scan IA one-shot a été lancé en local** (machine de Jean) le 2026-05-29 : 42 offres scorées selon `job_pref_rules` (21 new / 21 archived) et insérées via REST (service key).

## ADR-22 · 2026-05-31 · Jobs Radar — Engagement Manager comme rôle cible (scope tech/IA)

- **Contexte** : Jean (RTE, ex-manager PwC Digital) veut suivre les postes d'« engagement manager », alignés avec son poste actuel. Le radar (1) ne les cherche pas (aucune requête `engagement`/`delivery`), (2) les sous-note (rubric favorise BUILD/TRANSFO, pénalise le RUN : Workday « Sr Engagement Manager – AI Practice EMEA » = 3.5 → archived, vérifié en base), (3) ne permet pas de les isoler (`role_category` sans valeur dédiée). Ambiguïté du titre : « Engagement Manager » = standard du conseil MBB (**éliminatoire** chez Jean, ADR-21) OU lead delivery/transfo chez un éditeur tech (aligné RTE).
- **Décision** : périmètre **tech/produit/IA uniquement** — exclusion `conseil/ESN` (`job_pref_rules`, autorité absolue) **maintenue**. (1) **ÉTAPE 1 : 9 → 11 requêtes** (+ `engagement manager Paris`, `delivery manager Paris`). (2) **ÉTAPE 3** : EM/delivery/transformation manager devient un **rôle cible** si boîte tech/IA crédible + angle produit/transfo/IA avec ownership ; red flag explicite « RUN client pur / ESN-staffing » ; band salaire EM 85-120 k€. (3) **Nouvelle valeur `role_category` `em`** (migration `sql/017_jobs_em_category.sql`) + chip de filtre + label « EM » côté front (`panel-jobs-radar.jsx` + `CAT_DEF` de `data-loader.js`). (4) **Backfill curé one-shot** (MCP) : re-tag + re-score les seuls EM/delivery en boîte tech crédible ; conseil/ESN restent archivés et non re-taggés. Appliqué au prompt **live** via `RemoteTrigger update` (miroir [docs/cowork-routines/jobs-radar.md](../cowork-routines/jobs-radar.md)).
- **Conséquences** : quota JSearch ≈ **191 req/mois** (sous 200, ADR-20). Comme ADR-21, le scoring ne re-score pas le stock automatiquement → backfill **manuel et curé** (pas de `LIKE` aveugle ; la catégorie `em` ne reçoit que des boîtes tech crédibles). Statut user-owned jamais écrasé au backfill : flip `archived → new` **seulement si `user_verdict IS NULL`**. Blocage cloud JSearch `403` (ADR-21) **inchangé** : les nouvelles requêtes ne s'exécutent qu'en local / IP allowlistée. `pipelines.yaml` + `tab-jobs.md` + `index.json` mis à jour. Hors périmètre : assouplir l'exclusion conseil (MBB) ; refonte rubric FIT ; re-scoring hebdo automatique.

## ADR-23 · 2026-05-31 · Jobs Radar — le trigger d'héritage de statut n'hérite que des décisions utilisateur

- **Contexte** : `jobs_inherit_user_status` (migration 013) neutralise les republications LinkedIn en héritant du `status` archived/snoozed d'une ligne (title, company) récente. Mais il matchait **tout** `archived`, y compris les archivages **automatiques** (score < 5 au scan, sans verdict). Le 2026-05-31, AI6 « Head of Delivery » re-scoré **9.5** (nouvelles règles EM + fit assurance Malakoff Humanis) a été re-archivé en héritant d'un vieux archivage **auto** à 4.5 du 22 mai — enterrant le meilleur lead EM. Bug systémique : toute offre re-scorée à la hausse via republication était re-archivée.
- **Décision** : migration **018** — `jobs_inherit_user_status` n'hérite que d'un statut reflétant une **décision utilisateur** : `snoozed` (toujours user), ou `archived` **avec** (`user_verdict` renseigné **ou** `score_total >= 5`). Justification : la routine crée `new` dès score ≥ 5, donc un `archived` à score ≥ 5 ne peut venir que d'un archivage manuel ; un verdict 👍/👎 est explicite. Les archivages auto (archived + score < 5 + `user_verdict` NULL) n'écrasent plus les republications re-scorées. AI6 9.5 remis en `new` à la main.
- **Conséquences** : les offres re-scorées à la hausse remontent correctement ; les offres réellement rejetées (👎) ou snoozées restent neutralisées. Vérifié par 2 tests transactionnels (rollback) : republication d'un auto-archivé (AI6) → `new` ; republication d'un dismiss 👎 (Mistral TPM) → `archived`. `CREATE OR REPLACE FUNCTION` (le trigger BEFORE INSERT de 013 reste en place). Pas de re-scan du stock requis. Doc : `sql/018_jobs_inherit_status_userdriven.sql`, spec `tab-jobs.md`.

## ADR-24 · 2026-06-01 · Veille IA — contrainte `UNIQUE(url)` sur `articles` + ingestion idempotente

- **Contexte** : `articles` (table principale de la veille IA) était la seule table de contenu sans contrainte `UNIQUE(url)`. `main.py::save_to_supabase` postait en `Prefer: resolution=ignore-duplicates` mais sans `?on_conflict=url` ni contrainte → PostgREST résolvait les conflits sur la PK `id` (UUID toujours neuf), donc aucun dédup. Avec `LOOKBACK_HOURS=36` et un run quotidien, chaque article re-servi par un flux RSS deux jours de suite était ré-inséré. Constaté le 2026-06-01 : **244 doublons** (2030 → 1786 lignes uniques, jusqu'à 13 copies d'une même URL), visibles dans l'onglet Veille IA. Les 4 corpus satellites (anime/gaming/sport/news_articles) avaient déjà `UNIQUE(url)` → 0 doublon.
- **Décision** : migration **019** — `ALTER TABLE articles ADD CONSTRAINT articles_url_key UNIQUE (url)` (après dédup one-shot gardant la 1re capture par url), et `save_to_supabase` poste désormais sur `?on_conflict=url` comme les satellites. Les embeddings `memories_vectors` des lignes supprimées ont été re-routés vers l'article conservé (6 URLs sans couverture autrement) ou purgés comme redondants (55 vecteurs) — 0 orphelin, 0 collision `(source_id, chunk_index)`.
- **Conséquences** : les republications RSS sont silencieusement ignorées (`ON CONFLICT (url) DO NOTHING`) ; `articles` aligné sur le pattern satellites. **La contrainte doit exister avant que le code n'utilise `?on_conflict=url`** (sinon PostgREST 42P10 « no unique constraint matching ON CONFLICT ») → déployé contrainte-puis-push, hors fenêtre du cron `daily_digest` (06:00 UTC). Le dédup historique est une opération MCP one-shot, non rejouable. Doc : `sql/019_articles_url_unique.sql`.

## ADR-25 · 2026-06-04 · Jobs Radar — dédup logique (employeur+titre) + sélection d'URL durable (anti-lien-mort)

- **Contexte** : des hot leads pointaient vers des liens morts — Pigment « Engagement Manager » (`applied`) sur jobintree → HTTP **410**, BForBank « AI Program Manager » (`applied`) sur trabajo.org → instable. Cause racine double : (1) le dédup (ADR-19, ÉTAPE 2) ne portait que sur `linkedin_job_id` (= `job_id` JSearch), or JSearch syndique **une même offre sous plusieurs `job_id`** selon le feed source → **2 à 4 lignes par offre** (constaté : 22 clusters dupliqués actifs, dont Pigment EM en **3 exemplaires tous `applied`**) ; (2) `url = job_apply_link` brut → souvent un agrégateur jetable (jobintree/trabajo/hugodecrypte) qui expire en quelques jours, voire un **endpoint API `jsearch.p.rapidapi.com`** non cliquable (cas Doctolib). JSearch expose pourtant `apply_options[]` (avec un flag `is_direct` = lien ATS employeur) jamais exploité.
- **Décision** : correctifs **prompt-only** (pas de migration, pas de backfill de schéma). (1) **ÉTAPE 2 — dédup LOGIQUE** : clé `(employeur normalisé + titre normalisé)` (retire H/F, `(x/f/m)`, parenthèses, ponctuation, espaces, accents) sur les offres vues ≤ 45 j ; match si `job_id` connu **ou** clé logique identique → `UPDATE last_seen_date` sans re-scorer, **+ upgrade de l'`url`** si le nouveau lien est d'un palier plus durable. **Garde-fou anti-sur-fusion** : employeur générique/masqué (`Confidential`, vide) → jamais de fusion sur titre, dédup `job_id` seul. (2) **ÉTAPE 4 — CHOIX DE L'URL** : `apply_options[].is_direct=true` (ATS) → host le plus durable (lever/greenhouse/smartrecruiters/workday/ashby/WTTJ/`*.jobs`/`careers.*` > linkedin) → agrégateur ; **rejet absolu du domaine `jsearch.p.rapidapi.com`** (fallback = lien de recherche LinkedIn). Palier tracé dans `intel.link_source` ∈ {direct, durable, aggregator, search-fallback}. Appliqué au prompt **live** via `RemoteTrigger update` (miroir [docs/cowork-routines/jobs-radar.md](../cowork-routines/jobs-radar.md)).
- **Conséquences** : `intel` étendu = `{ …, link_source }` (offres existantes sans la clé — pas de backfill, champ diagnostique non lu par le front). Le dédup logique réduit fortement les lignes mais peut, en théorie, fusionner deux postes distincts au titre identique chez un même gros employeur (rare ; le garde-fou couvre les employeurs masqués ; réversible côté stock via `status`). Ne re-score pas le stock (cohérent ADR-21/22). **Nettoyage one-shot du stock** (MCP, hors routine) le 2026-06-04 : BForBank repointé vers l'ATS Crédit Agricole, Pigment EM marqué fermé (poste retiré de l'ATS Lever, 3 copies mortes), **~25 doublons archivés** (réversible : note datée + `status='new'`) ; 3 clusters laissés intacts (Euronext SPM `applied`+`new`, 2× `Confidential` — fusion jugée risquée). Blocage cloud JSearch `403` (ADR-21) **inchangé**. Doc : `pipelines.yaml` (`external_routines`, v2.4) + miroir `docs/cowork-routines/jobs-radar.md` mis à jour.

## ADR-26 · 2026-06-04 · Jobs Radar — vieillissement automatique (auto-archive des annonces non revues >30j)

- **Contexte** : sans mécanisme d'expiration, les leads `new` s'accumulent indéfiniment (332 `new` constatés le 2026-06-04, dont **120 non revus depuis >30j** — moyenne 40j, le plus vieux du 20/04). Or la routine (ADR-19, ÉTAPE 2) rafraîchit `last_seen_date` à chaque fois que JSearch renvoie encore l'offre : un `new` non revu depuis longtemps est donc une annonce **quasi certainement fermée** (futur lien mort). Le dédup logique + URL durable (ADR-25) empêche doublons et liens morts *à la création*, mais pas le **pourrissement** des offres après insertion.
- **Décision** : nouvelle **ÉTAPE 6 — Vieillissement** dans la routine (prompt-only, pas de migration) : `UPDATE jobs SET status='archived' WHERE status='new' AND last_seen_date < CURRENT_DATE - INTERVAL '30 days'`, note datée `auto-archive vieillissement` (réversible `status='new'`). **GARDE-FOU critique** : l'étape ne s'exécute QUE si le run a effectivement fetché des offres (`total_fetche > 0`) — un échec global JSearch (ex : `403` cloud, ADR-21) ne rafraîchit pas `last_seen_date` et archiverait à tort des offres vivantes. Ne touche QUE `status='new'` — jamais `applied`, `snoozed`, `user_verdict*`, `closed_at`. Tourne à chaque run (4×/sem) plutôt qu'hebdo (plus réactif ; le seuil 30j absorbe les échecs transitoires : une seule exécution réussie en 30j ré-arme `last_seen`). Appliqué au prompt **live** via `RemoteTrigger update` (miroir [docs/cowork-routines/jobs-radar.md](../cowork-routines/jobs-radar.md)).
- **Conséquences** : la vue `new` reste resserrée sur les offres réellement actives (~14j de fraîcheur). **Interaction avec ADR-23** : le trigger `jobs_inherit_user_status` hérite d'un `archived` quand `score_total >= 5` ; un lead auto-archivé à score ≥ 5 devient indistinguable d'un archivage manuel → une offre re-postée après auto-archivage ne ré-émerge pas d'elle-même (le dédup logique d'ADR-25 la matche et rafraîchit `last_seen` sans changer le statut). Jugé acceptable (rare ; toujours réversible à la main). **Cleaning one-shot** du stock le 2026-06-04 : 120 leads périmés archivés (108 sous-7 + 12 hot leads). Doc : `pipelines.yaml` (`external_routines`, v2.5) + miroir mis à jour.
